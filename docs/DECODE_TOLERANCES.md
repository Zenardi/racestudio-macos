# Decode conformance tolerances

The decode layer (M1) is validated against **libxrk** — XRKConverter's
pure-Python `.xrk` parser — as the golden **oracle**. The corpus-wide
conformance harness
([`core/racestudio-decode/tests/golden_e2e_test.rs`](../core/racestudio-decode/tests/golden_e2e_test.rs),
issue 1.8) decodes every `fixtures/*.xrk` with
[`decode_session`](../core/racestudio-decode/src/model.rs) and asserts its output
matches the committed `fixtures/golden/*.json` within the tolerances below. This
table is the single source of truth for those numbers; the harness references it.

## Why tolerances at all

The goldens are generated by `scripts/gen_goldens.py` from libxrk and store
per-channel **summary statistics** (`first`/`last`/`min`/`max`) **rounded to each
channel's own display precision** (`decimals`). The Rust decoder keeps raw
`f64` values, so a comparison rounds the decoded value to the same `decimals` and
requires it to land on the **same displayed value** — i.e. within **half a
display quantum** (`0.5·10⁻ᵈᵉᶜⁱᵐᵃˡˢ`), plus a tiny floating-point-noise margin.
This is uniform across channels: it is exact-to-the-last-decimal for a 2-dp
channel *and* for 8-dp latitude/longitude (≈1e-8), rather than a flat `1e-6` that
would leave the high-precision GPS channels ~100× looser than the goldens'
actual resolution.

Rounding uses `round_ties_even` to match Python's banker's `round()`; `min`/`max`
mirror NumPy's NaN propagation (any non-finite sample collapses them to `null`,
as `np.min`/`np.max` do), so the comparison never diverges from how the oracle
was generated.

## Tolerance table

| Aspect | Field | Comparison | Tolerance |
| --- | --- | --- | --- |
| **metadata** | driver, vehicle, track, session, series, log_date, log_time | string | **exact** |
| **metadata** | datetime_utc | integer (epoch s) | **exact** |
| **metadata** | channel_count, has_gps, lap_marker_count | container structural counts | **exact** |
| **channels** | name, unit | string | **exact** |
| **channels** | sample count | integer | **exact** |
| **channels** | sample_rate_hz | Hz | **1e-3** |
| **channels** | first / last / min / max | value, rounded to `decimals` | **½ display quantum** (`0.5·10⁻ᵈᵉᶜⁱᵐᵃˡˢ`) |
| **gps** | has_gps, fix_count, channel count | integer / bool | **exact** |
| **gps** | channel name, kind (Raw/Computed), unit | string | **exact** |
| **gps** | sample count | integer | **exact** |
| **gps** | latitude / longitude | value, rounded to `decimals` (= 8) | **½ display quantum** ≈ **5e-9** (enforces the 8-dp / ~1e-8 golden) |
| **gps** | altitude / speed / accuracy / pDOP / sats / fix | value, rounded to `decimals` | **½ display quantum** |
| **laps** | lap_count, best_lap_index | integer | **exact** |
| **laps** | lap index | integer | **exact** |
| **laps** | duration_s, start_time_s | seconds | **1e-3** (millisecond-precise beacon markers) |

### Notes

- **Latitude / longitude (~1e-8).** The `GPS Latitude`/`GPS Longitude` golden
  channels carry `decimals = 8`, so the half-quantum tolerance (~5e-9°) requires
  the decoded value to round to the golden's exact 8th decimal — the precision at
  which the clean-room ECEF→geodetic (Vermeille 2003) transform matches libxrk
  (verified: the corpus matches to exact 8-dp).
- **Beacon vs GPS laps.** The lap golden is the **beacon** lap-marker table
  (AiM's own recorded times); its per-lap durations are millisecond-precise, so
  `1e-3` s is exact-to-the-millisecond, not a slack. libxrk's public `log.laps`
  is GPS-plane-crossing-refined and differs by 10–50 ms — the harness does not
  compare against it (see the 1.5 lap decode notes).
- **Structural counts vs decoded lists.** `channel_count` (distinct `CHS`),
  `has_gps`, and `lap_marker_count` (raw markers) are **container** counts and
  can legitimately exceed the decoded `Session` lists (channels with samples,
  deduplicated laps); the harness reads them from `open_container`, not from the
  `Session` accessors.
- **GPS channels belong to the `gps` aspect.** libxrk's computed GPS channels
  (`GPS_InlineAcc`, `GPS_LateralAcc`, `GPS_Yaw_Rate`) carry a `sample_rate_hz` in
  some channel goldens, but `decode_channels` never emits them — they are
  synthesized by `decode_gps`. The harness validates them only under the `gps`
  aspect and excludes them (by name, using the gps golden) from the `channels`
  comparison, so no channel is double-counted.
- **Absolute channel timecodes are not compared.** The channel goldens' optional
  `t_first_ms`/`t_last_ms` reflect libxrk's recording-start–offset channel time;
  the decoder keeps **raw logger timecodes**, which differ by a constant per
  session. Reconciling that offset is a decode-semantics decision outside this
  conformance issue (the 1.3 contract is names/units/rate/count + first/last/min/
  max **values**), so the harness asserts those and not the absolute timecodes.

## Adding a fixture

The harness is **data-driven**: drop a new `<name>.xrk` into `fixtures/` and its
`<name>.{metadata,channels,gps,laps}.json` into `fixtures/golden/` (via
`make fixtures`), and the corpus tests pick it up with no code change.
